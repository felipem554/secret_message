# Password Hashing, Salting & Peppering — Spec

Reference spec for how user-password storage *should* be designed, distilled from `docs/research/PASSWORD_HASHING_VIDEO_NOTES.md`. Kept in this repo as an engineering reference and as the applicability analysis for `secret_message` below — this project does not currently implement, and as of this writing does not need, any of the mechanisms described here (see [Applicability to secret_message](#applicability-to-secret_message)).

## Threat models

Any password-storage design has to defend against two distinct attacks:

| | Online attack | Offline attack |
|---|---|---|
| **Attacker access** | Live login endpoint only | A dump of the credentials table (breach/leak) |
| **Defeated by hashing/salting/peppering?** | No — a correct guess still authenticates | Yes — this is what the mechanisms below are for |
| **Primary mitigations** | WAF, rate limiting (IP/device/user), account lockout after N failures, MFA | Hashing + salting + peppering (this document) |

A production auth system needs both categories of defense; this spec covers only the offline side.

## Core mechanisms

### 1. Hashing

- Never store passwords in plaintext, under any circumstances.
- Store `hash(password)` using a one-way function: identical input and parameters always produce the same output, but the output cannot be reversed to recover the input.
- Use a hash function that is deliberately **slow and memory-hard**, the opposite of what you'd want from a general-purpose hash map. Speed is the attacker's resource; a memory-hard, CPU-expensive function turns brute force into a billions-of-years problem at current compute power for a sufficiently long (16–24 char, mixed-charset) password.
- **Recommended algorithm: Argon2id.**

### 2. Salting

- Hashing alone still lets identical passwords produce identical hashes, enabling precomputed-hash-table attacks and cross-user/cross-app password inference (if a user reused a password on a weaker, breached service, an attacker can match hashes across services).
- Fix: mix a random, per-user **salt** into the input before hashing. Salt is not secret — store it alongside the hash in the same row/table.
- Salt must be: generated by the same library used for hashing (don't hand-roll it), sufficiently random and large, and **unique per user**. Reused salts reintroduce cross-user inference.

### 3. Peppering (optional, higher risk/reward)

- Even with hash + salt known to an attacker (full DB dump), a second, secret, **application-wide** value — the **pepper** — can be mixed in.
- Unlike the salt, the pepper is **not stored in the database**. It lives in a separate secret store (e.g. AWS Secrets Manager, Google Secret Manager), so a DB leak alone does not expose it.
- Correctly combining hash + salt + pepper is currently considered infeasible to break offline, for a reasonably long password.
- **Operational risk**: because the pepper lives outside the credentials table, losing it, rotating it incorrectly, or a bad deploy that changes it silently invalidates *every* stored password hash at once — 100% of users locked out, no recovery except a mass password reset. This blast radius is why pepper is considered optional/controversial, and why it demands the same operational rigor as any other single-point-of-failure secret.

## Implementation guidance

In priority order, from most to least hands-on:

1. **Well-established library, own storage** — use Argon2's reference implementation/bindings per its documentation. Do not invent a custom hashing or salting scheme.
2. **Higher-level auth framework** (e.g. Better Auth–style libraries) — delegate hashing/salting/storage correctness to a maintained library. Reasonable default when the team has no dedicated security expertise.
3. **Identity Provider** (Clerk, Auth0, AWS Cognito, etc.) — full outsourcing; the provider owns credential storage entirely.
4. **Avoid passwords entirely** — magic-link email login or OAuth (Google/GitHub/etc.) sidesteps the problem for B2C products where it's an option.

Across all options: verify whatever hashing/encryption is in place is a currently-recommended algorithm, not something legacy or already considered breakable.

## Applicability to secret_message

`secret_message` has no user accounts and stores no user passwords. Its data model is: `messages:<id>` (AES-256-encrypted payload) and `attempts:<id>` (wrong-key counter), both TTL'd in Redis — see `CLAUDE.md` and `docs/STORAGE_NATS_VS_REDIS.md`. There is no `PasswordEncoder`, no login flow, and no credential table anywhere in the codebase. **Argon2id and the hash/salt/pepper model in this document do not apply directly** — there is no password to hash.

That said, two structural parallels from this spec are already reflected in the codebase, and are worth naming explicitly since they came from the same underlying reasoning:

- **Pepper ≈ `IDEMPOTENCY_MASTER_KEY` (MIEK).** The spec's pepper — a secret, application-wide value stored outside the primary datastore, used to protect per-record secrets — is architecturally the same shape as the MIEK described in `docs/MEMORY_HARDENING.md`: idempotency records store their AES key encrypted under a server-held master key, not in the clear, and not derivable from the Redis dump alone. The pepper's operational risk (lose it → mass, unrecoverable lockout) applies equally to the MIEK: losing or rotating it incorrectly would make every stored idempotency record's AES key unrecoverable.

  This parallel surfaced one concrete gap, since fixed: `IdempotencyKeyVault` validated the MIEK's presence/shape but never checked whether it was still the checked-in dev-fallback value when running in production — the same class of mistake the pepper warning is about (a shared/default secret protecting production data). `IdempotencyKeyVault` now fails fast at startup when `app.env` (env `APP_ENV`) is `production` and the resolved master key still equals the dev fallback, mirroring the existing `DEBUG`+`APP_ENV` fail-fast pattern in `docker-entrypoint.sh`. See `IdempotencyKeyVault` and `IdempotencyKeyVaultProductionGuardTest`.
- **Online-attack mitigations ≈ existing rate limiting.** The spec's online-attack defenses (per-IP/device/user rate limiting, lockout after repeated failures) are the same category as this project's `RateLimitFilter` (100 req/day/IP, see `docs/RATE_LIMITING.md`) and the reveal endpoint's 3-strike `attempts:<id>` counter (see `CLAUDE.md` § Security model). Different attack surface (guessing a message's AES key vs. guessing a password), same underlying pattern: cap the number of guesses an online attacker gets. No gap found here — already adequately covered.

**Conclusion**: Argon2id/hashing itself doesn't apply — no user passwords exist to hash. The pepper parallel did surface one real, now-fixed gap (production dev-fallback-key guard). If the project ever grows a user-auth feature (e.g. an account system, or an optional password on individual secret messages), this document is the starting reference and Argon2id is the recommended algorithm at that time.
